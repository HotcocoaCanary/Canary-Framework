# 架构

框架是普通 Python 类之上的一层薄封装。它把**声明**（写在类上的标记）与**解释**（读取
标记并驱动的引擎）分开。

## 分层

```
errors            异常，任何一层都可使用
   ▲
meta              声明层：phase / dep / introspect
   ▲
flow              运行层：scope / graph / invoke / advance / unwind
   ▲
canary            门面：Canary 基类与 dep()
```

依赖方向严格单向：`canary → flow → meta → errors`。只有 `canary` 同时依赖两边，
那正是门面的职责。

这条约束不只是文档里的说法——`tests/test_layering.py` 用 `ast` 解析每个模块的 import
并断言方向，任何一次反向依赖都会让测试失败。

## 模块

| 模块 | 内容 |
|---|---|
| `core/errors.py` | 五个异常，全部继承 `CanaryError` |
| `core/meta/phase.py` | `Phase` 与 `init` / `start` / `stop` |
| `core/meta/dep.py` | `Dep` 描述符 |
| `core/meta/introspect.py` | 一次 MRO 遍历读出依赖与钩子，按类缓存 |
| `core/flow/scope.py` | `Scope`、`scope_of`、无参构造 |
| `core/flow/graph.py` | 构建依赖图、检测环 |
| `core/flow/invoke.py` | 调用一个钩子 |
| `core/flow/advance.py` | 在图上推进一个阶段，依赖在前 |
| `core/flow/unwind.py` | 在图上回收，依赖者在前 |
| `core/canary.py` | `Canary` 基类与 `dep()` |

## 标记，而非改造

装饰器只在方法上写一个标记，从不改造类。单元因此保持普通类的一切性质：可继承、可混入、
可嵌套。

| 标记 | 由谁写入 | 由谁读取 |
|---|---|---|
| `__canary_phases__` | 阶段装饰器 | `introspect`（哪些方法属于哪个阶段） |
| `_canary_scope` | `Scope.adopt` | `Dep.__get__`（从哪里取回依赖） |

依赖不用标记表达，它就是一个类属性（`Dep` 描述符），因此持有的是类对象本身而不是名字。

## 钩子解析

一次 MRO 遍历同时收集依赖与带标记的属性名，结果按类缓存——声明在类创建之后不再变化。

钩子按**属性名**解析，因此语义与普通方法完全一致：

- 子类覆盖同名钩子即替换，需要叠加时使用 `super()`。
- 子类覆盖但不再标记时，该钩子不再运行。
- 不同名的混入钩子各自成立，基类在前。

## 依赖图

一个单元第一次被推进时，连同它的全部依赖一起加入作用域的依赖图。节点是单元登记的类型，
边来自 `dep()` 声明，并按 `Scope.provide()` 的替换解析。图是静态的——`dep()` 是类上的
声明，生命周期开始之后不再接受替换——因此只构建一次，此后不变。

构建是一次迭代的深度优先遍历。**环**在这时被发现，早于任何钩子运行，并携带走到环上的
路径。一个节点在它的依赖都加入之后才加入，因此图的插入顺序本身就是一个拓扑序。

## 两条规则

**推进**依赖在前。本次调用涉及的每个节点一个任务：等它的依赖完成，再运行它的钩子。互不
依赖的单元因此同时推进，也没有任何递归。记录的是推进本身（一个 future）而非完成标志，
因此"未开始 / 进行中 / 已完成"不需要状态机：键不存在、未完成、已完成即是三态。另一次
调用正在推进的节点只被等待，不会再运行一遍。

**释放**本单元在前。释放一个单元时，它仍被使用——有依赖者正在启动、运行或停止——则跳过，
否则执行它的撤销钩子；无论哪种，随后都以同样的方式尝试它的每个依赖，同时进行，各在一个
任务里。被跳过或本就未运行的单元，一次调用中只被穿过一次；真正停止的单元每次都级联到依赖，
因为某个依赖可能刚刚失去最后一个使用者。一次调用的工作量因此与图的规模成正比。

两条规则在同一张图上互为镜像，正是这种对称让 `stop()` 与 `init()`、`start()` 一样成为
单元的动作。一个阶段用 `undo` 声明撤销它的阶段；`start` 的是 `stop`。

## 并发与失败

一个失败不会取消其他单元：每个节点各自完成。依赖未能全部完成的节点不运行钩子，以同一个
异常失败。阶段声明了 `undo` 时，失败或被取消的节点立即释放自己——不检查是否被使用，因为
等待它的依赖者从未用到它——再尝试它的依赖。因此一次失败的推进返回时，它启动的一切都已
释放，仍被其他运行中单元使用的除外。

失败随后还原为真实的失败——经多条路径到达的同一个失败只报告一次。等待另一个节点的推进
不会取消它。调用方取消推进时，同样的回滚在取消传播之前完成；取消无法携带的撤销钩子异常
交给事件循环的异常处理器。

台账记录进入过某个阶段的单元：`@start` 执行到一半失败的单元需要 `@stop`，正是靠它得知。

## 不变量

1. 单元一律由框架无参构造。
2. 一个作用域内，每个类型只有一个实例；两个各自构造的根是两张互不相干的图。
3. 装饰器只声明、不改造，单元保持普通类。
4. 依赖在 `@init` 之后才可用。
5. 全部 `@init` 完成之后，才有任何 `@start` 运行。
6. `stop()` 是唯一的回收路径，正常结束与失败结束共用，重复调用幂等。回收同时撤销
   `start` 的推进记录，因此图可以再次启动。
7. 有依赖者正在启动、运行或停止时，一个单元不会被停止。
8. 失败的 `start()` 在释放它启动的一切之后才返回。
9. 环在任何钩子运行之前被报告。
10. 框架不认识任何外壳，接入宿主只有上下文管理器与三个显式方法两条路。
