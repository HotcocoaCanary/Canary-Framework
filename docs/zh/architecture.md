# 架构

框架是普通 Python 类之上的一层薄薄的分层。它把**声明**（类上的标记）与**解释**（读取标记
的运行时）分开。

## 分层

```
common   — 共享的类型、异常与元数据标记（不含框架逻辑）
   ▲
core     — 声明层原语：@cocoa、@on_init/@on_start/@on_stop、自省
   ▲
runtime  — 引擎：Canary、建图、拓扑排序
```

依赖方向严格无环：`runtime → core → common`。每层只认识它的下一层。

包内一律走全路径模块名 —— 各层的 `__init__.py` 只有 docstring，不做转发导出。对外的公开
API 只有一处出口：`canary_framework`。

## 标记，而非魔法

框架通过**标记**沟通 —— 装饰器给类和方法盖上小的字符串常量，运行时再读回它们。所有标记
都收口在 `canary_framework.common.markers`：

| 标记 | 由谁写入 | 由谁读取 |
|---|---|---|
| `COCOA_ATTR` | `@cocoa` | runtime（是否是单元？依赖有哪些？） |
| `ON_INIT` / `ON_START` / `ON_STOP` | 钩子装饰器 | runtime（执行哪些钩子） |

装饰器只 `setattr` 一个标记，从不改造类。这让单元保持普通类，也让自省廉价、无副作用。

MRO 扫描只有一份实现，一遍走完把三种钩子标记分好桶，结果**按类缓存** —— 它在类创建之后
不再变化，而一次完整生命周期要扫三遍（init / start / stop）。跳过 `object`：它有二十多个
可调用成员，一个都不可能带我们的标记，而每个类的 MRO 末端都是它。

## 两个阶段

1. **声明** — `@cocoa(deps=[...])` 记录依赖，`@on_init`/`@on_start`/`@on_stop` 记录钩子。
   此时什么都不运行。
2. **解释** — `Canary` 读取标记、建图、排序、注入、驱动生命周期。这个切分让纯图算法可以
   独立测试。

## 引擎

`Canary.__init__` 只校验根。`init()` 建图（每个类型无参构造一次）、跑卡恩拓扑排序、按序
注入依赖并执行 `@on_init`；`start()` 按序执行 `@on_start`；`stop()` 逆序执行 `@on_stop`。
排序是确定的，成环以 `CircularDependencyError` 暴露。

建图用显式栈而非递归，依赖链的深度因此不受 Python 递归上限约束。构造是先调用、出了
`TypeError` 再回头看签名，`inspect.signature` 只在失败路径上运行。

图上的实例**全部由框架构造**，没有第二条来源 —— 所以"这个单元是怎么来的"永远只有一个
答案，构造失败与生命周期失败也因此有统一的处置方式。

## 它不认识任何外壳

`Canary` 只做装配与生命周期。HTTP、CLI、定时任务、消息消费者 —— 这些都是**外壳**，由别的
库负责，Canary 不认识它们中的任何一个。

接进去只有两种形状，因为 Python 世界只有这两种：宿主收一个异步上下文管理器，或者收成对的
启动 / 关停回调。

```python
app = FastAPI(lifespan=canary.lifespan)      # 形状一：ASGI、MCP、FastStream
                                             # 形状二：start() 与 stop() 两个显式方法
```

## 不变量

1. **cocoa 是最小运行单元。** 依赖、状态与生命周期都标记在同一个类上。
2. **装饰器只声明、不改造。** 单元保持普通类，可继承、混入、嵌套。
3. **实例全部由框架无参构造。** 需要外界输入的事一律发生在生命周期钩子里，因为只有那里
   的事情才有对应的回收步骤。
4. **装配是同步的、无副作用的。** 建图、排序、注入不跑任何钩子，也不需要事件循环。
5. **装配期能发现的错误一律在装配期抛出。** 撞名、成环、需要构造参数、依赖不是 cocoa。
6. **运行时不认识任何外壳。** 接入宿主只有 `lifespan` 与三个显式方法两条路。
